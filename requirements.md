# Требования к фреймворку бектестирования (ADR)

> Документ ведётся по методике **ADR** (Architecture Decision Record): каждое
> архитектурное решение фиксируется отдельной записью с полями *Статус*,
> *Контекст*, *Решение*, *Последствия*. Пока мы на этапе сбора требований,
> статус всех записей — `Предложено` (Proposed); по мере согласования они будут
> переводиться в `Принято` (Accepted).

---

## ADR-0001: Абстракция источника данных

- **Статус:** Предложено
- **Контекст:**
  Ядру бектеста нужны рыночные данные, а источник этих данных не должен влиять
  на логику стратегий. Первоначально поддерживаются два источника — **CSV
  файлы** и **ClickHouse**. Ожидается, что в будущем появятся новые (Parquet,
  бинарные файлы, Redis/потоковые источники, …). Добавление источника не должно
  требовать переписывания ядра.
- **Решение:**
  - Единый интерфейс `DataSource` (абстрактный), единый для всех бэкендов.
  - Реализации-адаптеры: `CsvDataSource`, `ClickHouseDataSource`.
  - Фабрика/реестр источников: источник создаётся по конфигурации (ключ типа +
    параметры подключения), новые бэкенды регистрируются без правки ядра.
  - Все источники возвращают данные в **едином типизированном формате**
    (см. ADR-0002), а не в нативном представлении конкретного хранилища.
- **Последствия:**
  - Стратегия пишется против интерфейса, а не против формата файла/БД.
  - Отрицательный эффект: накладные расходы на унификацию форматов; схема
    должна покрывать все типы данных (см. ADR-0002), иначе интерфейс придётся
    ломать.
  - См. также ADR-0006 (пакетная выгрузка) и ADR-0007 (CSV → ClickHouse):
    они уточняют, как именно источники отдают данные при объёмах, не
    помещающихся в память.

## ADR-0002: Типы таблиц и фиксированные схемы

- **Статус:** Предложено
- **Контекст:**
  Рыночные данные неоднородны: сделки (тики), срезы стакана, инкремент-апдейты
  стакана. У каждого вида — свой набор полей. Чтобы интерфейс `DataSource`
  оставался стабильным, а код стратегий — типобезопасным, вводится конечный
  перечень «типов таблиц», у каждого из которых жёстко зафиксирован набор и
  типы колонок.
- **Решение:**
  - Конечное множество типов таблиц. Каждый тип = фиксированная схема: набор
    колонок с именами и типами. Имена колонок **принадлежат типу** и не могут
    меняться от источника к источнику.
  - Перечень типов (согласован с заказчиком):

    | Тип              | Описание                                  | Источник-ориентир (Binance)              |
    |------------------|-------------------------------------------|------------------------------------------|
    | `trades`         | сырые сделки (тики)                       | REST `/api/v3/trades`, WS `trade`        |
    | `depth_snapshot` | полный срез стакана (снепшот)             | REST `/api/v3/depth`, WS partial depth   |
    | `depth_diff`     | разница уровней стакана (инкремент-апдейт)| WS diff-depth stream                     |

  - Именование колонок: `snake_case`.
  - Уровни стакана хранятся **в плоском виде**: одна строка = один уровень
    (см. ADR-0003).
- **Последствия:**
  - Строгая типизация на этапе компиляции; несоответствие схемы источника
    обнаруживается при загрузке, а не в рантайме стратегии.
  - Отрицательный эффект: добавление нового типа таблицы — это изменение ядра
    (схемы), а не «просто ещё один файл».

## ADR-0003: Схемы колонок

- **Статус:** Предложено
- **Контекст:**
  Канонические схемы, производные от полей Binance (REST + WebSocket). Имена —
  `snake_case`, осмысленные (не сырые ключи Binance вроде `a`, `p`, `q`).
  Уровень стакана — пара `(price, qty)`; хранится плоскими строками, поэтому в
  стаканных таблицах каждая строка несёт `side`, `price`, `qty`.
- **Решение:**

  ### `trades` — сырые сделки

  | Колонка         | Тип             | Поле Binance | Примечание |
  |-----------------|-----------------|--------------|------------|
  | `symbol`        | string          | `s`          | инструмент |
  | `trade_id`      | int64           | `t`          | id сырой сделки |
  | `price`         | float64         | `p`          | цена |
  | `qty`           | float64         | `q`          | объём |
  | `trade_time`    | `utxx::time_val`| `T`          | время сделки |
  | `is_buyer_maker`| bool            | `m`          | покупатель — мейкер |

  *Исключено (по решению):* `buyer_order_id` (`b`), `seller_order_id` (`a`),
  `event_time` (`E`), `quote_qty` (`quoteQty`).

  ### `depth_snapshot` — плоский срез стакана

  | Колонка           | Тип             | Поле Binance | Примечание |
  |-------------------|-----------------|--------------|------------|
  | `symbol`          | string          | `s`          | инструмент |
  | `first_update_id` | int64           | `U` (WS); `lastUpdateId` (REST) | первый id события |
  | `final_update_id` | int64           | `u` (WS); `lastUpdateId` (REST) | последний id события |
  | `side`            | enum(bid,ask)   | —            | сторона уровня |
  | `level`           | int32           | —            | позиция уровня (0 = лучшая цена); хранится явно |
  | `price`           | float64         | —            | цена уровня |
  | `qty`             | float64         | —            | объём на уровне |

  ### `depth_diff` — плоский инкремент-апдейт

  | Колонка           | Тип             | Поле Binance | Примечание |
  |-------------------|-----------------|--------------|------------|
  | `symbol`          | string          | `s`          | инструмент |
  | `first_update_id` | int64           | `U`          | первый id события |
  | `final_update_id` | int64           | `u`          | последний id события |
  | `side`            | enum(bid,ask)   | —            | сторона уровня |
  | `price`           | float64         | —            | цена уровня |
  | `qty`             | float64         | —            | объём; `0` — удалить уровень |

- **Последствия:**
  - Плоский вид упрощает CSV (нет вложенных массивов) и загрузку в ClickHouse.
  - Отрицательный эффект: один снепшот «распадается» на N строк; для
    восстановления среза нужна группировка по `(symbol, final_update_id)`.

## ADR-0004: Представление времени

- **Статус:** Предложено
- **Контекст:**
  Binance отдаёт время в миллисекундах (`int64` ms). Внутреннему ядру нужен
  единый, точный и удобный для арифметики тип времени, не зависящий от
  источника.
- **Решение:**
  Канонический внутренний тип времени — `utxx::time_val` (секунды + наносекунды).
  В CSV время сериализуется **одним полем** вида `секунды.наносекунды`
  (например `1699999999.123456789`). В ClickHouse используется нативный тип
  `DateTime64(9, 'UTC')` (конверсия `time_val` ↔ `DateTime64` на границе
  адаптера).
- **Последствия:**
  - Единый тип во всех таблицах и структурах ядра.
  - Отрицательный эффект: на границе ClickHouse нужна конверсия
    `utxx::time_val` ↔ `DateTime64(9)`. Конверсия обратима (точность 9 знаков
    = наносекунды).

## ADR-0005: Физическая раскладка CSV

- **Статус:** Предложено
- **Контекст:**
  CSV — один из двух источников данных. Нужен стабильный физический формат:
  раскладка файлов, наличие заголовка, сериализация типов.
- **Решение:**
  - Раскладка: **один файл = один инструмент + один тип таблицы**
    (например `BTCUSDT_trades.csv`).
  - `symbol` **не хранится колонкой** в CSV — восстанавливается из имени файла.
  - Время — одно поле `секунды.наносекунды` (см. ADR-0004).
  - Формат строки: RFC 4180, разделитель `,`.
  - Заголовок: допускаются **оба варианта** — файл с первой строкой-заголовком
    или без неё (флаг в конфигурации источника). Порядок колонок в любом случае
    фиксирован схемой типа.
- **Последствия:**
  - `symbol` в CSV — внешние метаданные (имя файла), а не колонка; читающий
    код должен парсить имя файла. В ClickHouse `symbol` остаётся обычной
    колонкой (см. открытый вопрос №4 о единообразии).

## ADR-0006: Пакетная (потоковая) выгрузка данных

- **Статус:** Предложено
- **Контекст:**
  Объёмы рыночных данных могут достигать терабайт и не помещаются в оперативную
  память. Ядро не может загрузить весь набор разом. Стратегии должны обрабатывать
  данные потоком, а источник — отдавать данные частями (батчами) в текущий
  рабочий набор.
- **Решение:**
  - `DataSource` отдаёт данные **батчами**: ядро запрашивает очередную порцию
    данных через итератор (`next_batch()`), обрабатывает её и запрашивает
    следующую. Ни один адаптер не материализует весь набор в память.
  - Гранулярность батча — **временное окно** (например час/день), настраиваемое;
    как защита от пиков допускается верхняя граница числа строк.
  - Источник **гарантирует** порядок данных по «естественному ключу» типа
    (см. ниже); внутри батча и между батчами порядок не нарушается.
- **Последствия:**
  - Стратегия обязана быть потоковой (stateful): она не имеет «глобального
    взгляда» на весь ряд, только на текущий батч + переносимое состояние.
  - Отрицательный эффект: это жёсткое ограничение на класс алгоритмов
    (нельзя «посмотреть в будущее», нельзя произвольный случайный доступ по
    всему ряду без повторного прохода).
- **Естественный ключ порядка по типам:**
  - `trades` — `(symbol, trade_time, trade_id)`;
  - `depth_snapshot` — `(symbol, final_update_id)`;
  - `depth_diff` — `(symbol, final_update_id)`.

## ADR-0007: CSV как staging-слой для ClickHouse

- **Статус:** Предложено
- **Контекст:**
  При терабайтных объёмах эффективная колоночная выборка по диапазону времени
  возможна только в ClickHouse. Читать CSV потоком с фильтром по времени —
  это полный скан файла, неприемлемо для бектеста. Поэтому CSV рассматривается
  как формат поставки/хранения, а не как формат произвольного доступа.
- **Решение:**
  Перед работой CSV-данные конвертируются в **таблицу ClickHouse в отдельной
  служебной БД** (staging-схема); дальнейшие выборки (по диапазону времени,
  инструменту, типу) выполняются через ClickHouse. `CsvDataSource` превращается
  в **ingestor** (загрузчик), а не в источник запросов. Исходный CSV **остаётся**
  как источник истины (не удаляется после ingest).
- **Последствия:**
  - ClickHouse становится фактическим движком запросов даже для CSV-данных, и
    является **обязательной** зависимостью фреймворка.
  - Эффективная колоночная выборка и потоковая выдача батчами (ADR-0006).
  - Отрицательный эффект: для работы с CSV нужен поднятый ClickHouse; время
    на ingest перед началом бектеста; повторный запуск требует либо повторного
    ingest, либо кэширования уже загруженной staging-таблицы.
